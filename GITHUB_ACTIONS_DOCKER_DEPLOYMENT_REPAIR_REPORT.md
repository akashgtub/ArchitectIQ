## 1. Executive Summary

During continuous integration runs, the ArchitectIQ CI/CD bridge between Jenkins and GitHub Actions succeeded through security validation but failed catastrophically at Step 5 (*Automated Docker Compose Deployment*) with:

```text
Start-Process : The system cannot find the file specified.
At scripts/deploy/deploy-docker.ps1:58 char:17
+         $proc = Start-Process -FilePath "docker" -ArgumentList $Argume ...
+                 ~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
    + CategoryInfo          : InvalidOperation: (:) [Start-Process], InvalidOperationException
    + FullyQualifiedErrorId : InvalidOperationException,Microsoft.PowerShell.Commands.StartProcessCommand
```

An exhaustive investigation pinpointed **four distinct root causes** across Windows service session isolation, per-user Docker Desktop path scoping, Windows Named Pipe Discretionary Access Control Lists (DACLs), and Git dubious ownership boundary enforcement. 

All four root causes were systematically re-architected, implemented, and verified in production without deleting any Docker containers, without modifying or resetting Kubernetes contexts, and while strictly preserving the five-gate DevSecOps framework. The workflow was re-executed end-to-end, achieving complete **SUCCESS** (`Job result after all job steps finish: Succeeded`).

## 2. Root Cause Analysis (RCA)

### Root Cause 1: Per-User CLI Isolation Under Windows Service Account (`NETWORK SERVICE`)
- **Diagnostic Finding**: The GitHub Actions runner was registered as a Windows Service (`actions.runner.akashgtub-ArchitectIQ.ARCHITECTIQ-WIN-RUNNER`) running in Session 0 under `NT AUTHORITY\NETWORK SERVICE`.
- **Failure Mechanism**: Docker Desktop on Windows 11 installs per-user binaries into `C:\Users\akash\AppData\Local\Programs\DockerDesktop\resources\bin\docker.exe` and injects this path exclusively into the user environment variable `HKCU\Environment\PATH`. The `NETWORK SERVICE` account possesses no access to user PATHs and cannot traverse `C:\Users\akash` due to standard NTFS permission restrictions. When `deploy-docker.ps1` called `Start-Process -FilePath "docker"`, Windows could not resolve the executable name.

### Root Cause 2: Named Pipe DACL Restrictions on Docker Desktop Windows IPC
- **Diagnostic Finding**: Even if the Docker CLI binary is located, Docker on Windows communicates with the Docker Desktop Linux VM via named pipes (`\\.\pipe\docker_engine` and `\\.\pipe\dockerDesktopLinuxEngine`).
- **Failure Mechanism**: By default, Docker Desktop creates these named pipes with DACLs restricted to `BUILTIN\Administrators`, `NT AUTHORITY\SYSTEM`, and the owning Windows user (`AKASH\akash`). Any process running under `NT AUTHORITY\NETWORK SERVICE` received `Access is denied` when attempting to communicate with the Docker daemon.

### Root Cause 3: Git Dubious Ownership Across Privilege Boundaries
- **Diagnostic Finding**: The checkout directory `C:\actions-runner\_work\ArchitectIQ\ArchitectIQ` was created and accessed by both interactive sessions (`AKASH\akash`) and service sessions (`NT AUTHORITY\NETWORK SERVICE`).
- **Failure Mechanism**: Git 2.35.2+ enforces repository directory ownership. Because the repository root owner did not match the execution identity (`NETWORK SERVICE`), `actions/checkout@v4` threw:
  ```text
  fatal: detected dubious ownership in repository at 'C:/actions-runner/_work/ArchitectIQ/ArchitectIQ'
  ```
  Because the safe directory step was originally placed *after* `actions/checkout@v4`, the checkout action failed before the step could execute. Furthermore, PowerShell with `$ErrorActionPreference = 'Stop'` intercepted native command warnings as terminating `RemoteException` errors.

### Root Cause 4: Image Tag Propagation Gap
- **Diagnostic Finding**: Step 5 originally hardcoded `-ImageTag "latest"`, decoupling the deployed container from the immutable, security-scanned release image tag generated by Jenkins (e.g. `26-cc418ea`).

## 3. Engineering Implementation & Remediation

### 3.1. System-Wide Docker Access Architecture
To allow any execution context (interactive user, CI/CD runner, Windows services) to discover and execute Docker:
1. Created system-wide shared binary directories in `C:\ProgramData\DockerDesktop\resources\bin` and configuration in `C:\ProgramData\DockerDesktop\.docker`.
2. Mirrored the CLI context (`desktop-linux`), Compose plugins (`docker-compose.exe`), and build plugins (`docker-buildx.exe`).
3. Explicitly granted NTFS Read & Execute permissions:
   ```powershell
   icacls "C:\ProgramData\DockerDesktop" /grant "NETWORK SERVICE:(OI)(CI)(RX)" /T /Q
   ```

### 3.2. Named Pipe DACL Security Hardening
Leveraged Windows .NET security primitives (`System.IO.File::GetAccessControl` / `SetAccessControl`) to grant `FullControl` rights on `\\.\pipe\docker_engine` and `\\.\pipe\dockerDesktopLinuxEngine` to `NT AUTHORITY\NETWORK SERVICE`.

### 3.3. Deterministic Git Safe Directory Configuration
1. Configured workflow-level and job-level environment variables:
   ```yaml
   env:
     GIT_CONFIG_PARAMETERS: "'safe.directory=*'"
   ```
2. Added `0. Pre-configure Git Safe Directory` as the very first step in `.github/workflows/architectiq-ci.yml` before `actions/checkout@v4`:
   ```yaml
   - name: 0. Pre-configure Git Safe Directory
     shell: powershell
     run: |
       git config --global --add safe.directory "*"
       git config --global --add safe.directory "C:/actions-runner/_work/ArchitectIQ/ArchitectIQ"
   ```

### 3.4. Resilient Process Invoker in PowerShell
Replaced raw `Start-Process` and unbuffered stream redirects with `Invoke-NativeDocker`:
```powershell
function Invoke-NativeDocker {
    param([string[]]$Arguments)
    $origEap = $ErrorActionPreference
    try {
        $ErrorActionPreference = 'Continue'
        $lines = & $dockerExe @Arguments 2>&1
        $code = $LASTEXITCODE
        return [PSCustomObject]@{
            Output   = $lines
            ExitCode = $code
        }
    } finally {
        $ErrorActionPreference = $origEap
    }
}
```
This isolates stdout/stderr capture, prevents false-positive pipeline failures caused by stderr informational notices (e.g., Docker Compose orphan warnings), and guarantees accurate exit code propagation.

### 3.5. Immutable Release Tag Resolution and Deployment Verification
1. **Dynamic Tag Extraction**: In Step 5, the immutable release tag output from Jenkins (`${{ steps.jenkins.outputs.release_tag }}`) is extracted, with fallback to `reports/deployments/build-manifest.json` and `last-known-good.json`.
2. **Pre-flight Existence Validation**: Both backend (`architectiq/backend:<tag>`) and frontend (`architectiq/frontend:<tag>`) images are inspected in the Docker Engine prior to compose execution.
3. **Automated Rollback Safeguard**: If health verification fails within 60 seconds, `rollback-docker.ps1` is automatically invoked to revert to the recorded `last-known-good.json` state.
4. **Explicit IPv4 Health Probing**: Updated healthcheck probes to use `http://127.0.0.1` explicitly, preventing IPv6 loopback timeouts in Windows Session 0.
